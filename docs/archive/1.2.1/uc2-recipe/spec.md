# 产品规格：菜品库管理（uc2-recipe）

## 问题与动机

家庭饮食计划需要可复用的标准菜品库。没有结构化菜品数据时，后续周计划、备菜采购、饮食记录和营养复盘都缺少稳定输入，只能依赖临时文本或人工记忆。本需求建立菜品管理能力，让用户能沉淀可筛选、可复用、可维护的家庭菜品。

## 目标用户

- 家庭饮食计划维护者：录入和维护家庭常做菜、宝宝菜、减脂菜等标准菜品。
- 后续计划生成能力：基于菜品类型、季节、人群、烹饪时长和营养信息选择候选菜品。

## 功能边界

**做什么（In Scope）**：

- 创建手动菜品，并维护菜品名称、类型、季节、人群、口味、难度、烹饪时长、封面图。
- 维护菜品食材、烹饪步骤和营养信息。
- 分页查询菜品，并按关键字、类型、季节、人群、宝宝友好、减脂友好、难度和最大烹饪时长筛选。
- 搜索菜品名称并返回轻量列表。
- 查看菜品详情。
- 更新菜品基础信息、食材、步骤、营养信息和状态。
- 删除手动菜品，删除后允许复用同名菜品。
- 对宝宝适配菜品自动体现宝宝友好属性。

**不做什么（Out of Scope）**：

- 不实现图片上传、图片审核或 CDN 管理。
- 不实现系统预置菜品导入流程。
- 不实现 AI 生成菜品、菜品推荐或周计划生成。
- 不实现食材库存、采购清单或备菜计划。
- 不实现营养目标达标计算或营养报告。
- 不提供前端页面。

## 用户场景

### 场景 1：新增家庭菜品

1. 用户填写菜品基础信息、食材、步骤和可选营养信息。
2. 系统保存菜品，并返回带唯一标识的菜品详情。
3. 用户后续可以在菜品库中查看和筛选该菜品。

### 场景 2：筛选和搜索菜品

1. 用户输入筛选条件或搜索关键字。
2. 系统返回匹配的菜品列表，并给出分页总数。
3. 用户可以打开某个菜品查看完整详情。

### 场景 3：维护已有菜品

1. 用户选择一个手动菜品。
2. 用户更新基础信息、食材、步骤、营养或状态。
3. 系统保存变更，后续查询和详情展示反映最新内容。

### 场景 4：删除并复用菜品名称

1. 用户删除一个手动菜品。
2. 系统不再在正常查询中展示该菜品。
3. 用户可以重新创建同名菜品，用于保留历史删除记录同时支持名称复用。

## 输入与输出（用户视角）

| 方向 | 用户提供/看到什么 | 约束（用户可感知的） |
|------|-------------------|---------------------|
| 输入 | 菜品名称、类型、季节、人群、口味、难度、烹饪时长、封面图、食材、步骤、营养信息 | 菜品名称不能为空；菜品类型不能为空；食材列表不能为空；营养值不能为负数 |
| 输出 | 菜品列表、分页总数、搜索结果、菜品详情、更新/删除结果 | 被删除菜品不出现在正常查询中；宝宝人群菜品会被标记为宝宝友好 |

## 验收标准

- Given 用户提供合法的菜品基础信息和食材列表, When 创建菜品, Then 系统返回菜品详情且包含持久化后的食材、步骤和营养信息。
- Given 已存在同名未删除菜品, When 用户再次创建同名菜品, Then 系统拒绝创建并提示名称冲突。
- Given 菜品人群为宝宝, When 用户创建或更新菜品, Then 系统将该菜品标记为宝宝友好。
- Given 用户提供负数营养值, When 创建或更新营养信息, Then 系统拒绝该请求。
- Given 菜品库中有多种类型菜品, When 用户按类型、季节、人群、难度或烹饪时长筛选, Then 系统只返回符合条件的菜品并返回正确总数。
- Given 用户删除手动菜品, When 再次查询菜品列表或详情, Then 被删除菜品不再作为有效菜品返回。
- Given 一个菜品名称只存在于已删除记录中, When 用户创建同名菜品, Then 系统允许创建。
- Given 菜品来源为系统预置, When 用户尝试编辑或删除, Then 系统拒绝操作。

## 异常与边界情况

| 场景 | 触发条件 | 预期行为 |
|------|----------|----------|
| 必填信息缺失 | 菜品名称、类型或食材列表为空 | 拒绝请求，提示输入不合法 |
| 名称重复 | 同名有效菜品已存在 | 拒绝创建，避免有效菜品重名 |
| 营养值非法 | 热量、蛋白质、脂肪、碳水、膳食纤维、钙、钠任一值为负数 | 拒绝保存营养信息 |
| 系统菜品被修改 | 用户尝试编辑或删除系统来源菜品 | 拒绝操作 |
| 删除后复用名称 | 同名菜品均已删除 | 允许重新创建同名菜品 |
| 查询无结果 | 筛选条件没有匹配菜品 | 返回空列表和总数 0 |

## 产品约束

- 菜品库必须服务家庭饮食规划，不做泛菜谱社区能力。
- 手动菜品和系统菜品要区分；系统菜品不能被普通维护操作破坏。
- 删除不应阻断同名菜品重新录入。
- 菜品数据必须能支撑后续周计划、采购和营养复盘的结构化消费。

## 度量与成功标准

- 用户可以通过后端 API 完成菜品创建、查询、更新和删除闭环。
- 菜品详情包含基础信息、食材、步骤和营养信息，能作为后续计划生成输入。
- 核心创建、筛选、删除复用场景有自动化测试覆盖。
